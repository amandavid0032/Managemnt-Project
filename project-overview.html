Project overview · updated 14 Nov 2026

EduHub

An education platform with two halves: students and parents find and compare schools, and schools run their day-to-day work (notices, attendance, fees, hostel) on the same system, with one login for everyone.

01What we are building

A discovery site, a school management tool and a student profile, all in one system

Discovery

Anyone can search and browse published schools, colleges, universities and training centres, without signing in.

Institution management

Schools manage their own students, teachers and staff. Later they also manage notices, attendance, fees and hostel rooms.

Student portal & profile

A student signs in once to see their school life, and carries an education history across schools, a bit like LinkedIn.

Every feature has two sides

A student can only see something after the school creates it, so each feature is built in pairs. The school's side is usually the bigger job.

02The core ideas

Four decisions that shape the whole codebase

A school is not a login

A school is a row in institutions. Only people log in. A person is connected to a school through a membership, so one person can be a student at one school and a teacher at another.

Two separate kinds of power

Platform role (USER, PLATFORM_ADMIN, SUPER_ADMIN) covers the whole site.
Membership role (STUDENT, TEACHER, STAFF, INSTITUTION_ADMIN) covers one school only.

One database for all schools

All schools share one PostgreSQL database and every school-owned row carries an institution_id. That's what makes "search all schools" possible. The TenantGuard keeps School A from ever reading School B's data.

One login page for everyone

Super admins, school admins, teachers and students all use /login. The server says who you are, and the app sends admins to /admin and everyone else to /.

users ──────────────┬─< refresh_tokens
                    └─< institution_memberships >── institutions ──┬─< institution_external_ids
                                                                   └─< institution_media

The six database tables today. Everything planned (notices, fees, hostel…) will attach to these.

03What is built so far

Phases 1 and 2 are built and tested. Neither has been clicked through in a browser yet.

Database & API done

PostgreSQL 16, 8 tables, 4 migrations. NestJS API with auth, institutions, memberships, users, profiles, school dashboard, mail and health modules.

Login & sessions done

Register, login, logout, logout from all devices, and automatic token refresh. Passwords hashed with Argon2id.

Login page in the browser done

/login page, session kept across reloads, Sign in / Sign out in the header.

Super admin panel done

Dashboard with real counts, create, edit, publish and archive institutions, view members, search users, and suspend or reactivate them.

Public discovery done

Homepage lists published institutions with search, filters and pagination.

Automated tests done

227 API end-to-end tests in 8 suites, 2 API unit tests and 24 frontend tests, including tests that prove one school cannot read another's data.

Clicked through in a browser not yet

Every screen compiles, every endpoint is tested, and the main flows passed a check against the running server. Nobody has gone through the checklist below in a browser yet.

Profiles & education history done

Headline, bio, location and a visibility setting (only me / signed-in users / everyone). Education history comes from the schools' own records and keeps past schools.

School dashboard done

/school/:slug for school admins and staff: real member counts, the school's details, and member management (add, change role, suspend, end).

Password reset & email verification done

Emailed single-use links. A school can only add someone whose email is verified. Emails print to the API log in development; production needs SMTP.

Student & teacher dashboards later

Nothing to show them yet. They arrive with Notices and Attendance.

Notices, attendance, fees, hostel planned

No tables, API or screens yet. These are phases 3–6.

An institution's life cycle

DRAFT ──► PENDING_REVIEW ──► PUBLISHED ◄──► SUSPENDED
  ▲              │               │
  └──────────────┴───────────────┘        DELETE ──► ARCHIVED (final)

New institutions always start as DRAFT. Only PUBLISHED ones appear on the public homepage. Status changes go through their own endpoint (PATCH /institutions/:id/status) so a normal edit can never publish something by accident.

05How login works

Two tokens: a short one for each request and a long one to renew it

TokenLastsKept inUsed for
Access token (JWT)15 minutesBrowser memory onlySent with every API request
Refresh token30 dayshttpOnly cookie (JavaScript can't read it)Getting a new access token
 
LOGIN      browser ──email + password──► API ──► checks password, account is ACTIVE
           browser ◄── access token + refresh cookie

REQUEST    browser ──access token──► API re-reads the user from the database every time

15 MIN     API says 401 ──► app silently refreshes once ──► retries the request

LOGOUT     refresh token revoked + cookie cleared
LOGOUT ALL every session for that user is killed at once
Why it's safe: roles are read from the database, never trusted from the browser. Suspending a user takes effect immediately. A reused refresh token kills the whole session chain. Wrong email and wrong password give the same error message. A user asking for another school's data gets 404, so they can't even tell whether it exists.

PHASE 5

PHASE 6

PHASE 7
planned

Social layer

Follow people and schools, posts, a feed and messaging. It comes last because a feed with no people in it is worse than no feed.

07Jobs & admissions

The LinkedIn-style part, and why admissions comes first

An admission form and a job post work the same way underneath: someone publishes an opening, someone submits an application, and it moves through a pipeline (applied → shortlisted → interview → decided). If we build that once, all of these come from it:

TypeWho postsWho appliesWhen
AdmissionsSchool: a course with seatsStudentsbuild first
Teacher hiringSchool: a vacancyTeacherssecond
InternshipsCompaniesStudentsmuch later
Alumni network——comes with profiles

Admissions goes first because students already want to apply to a particular college. A job board with no visitors gets no second post, but a school gets value from its very first applicant.

08Tech stack

What it is built with, and what we chose not to use

PartTechnology
BackendNestJS 11, TypeScript (strict)
DatabasePostgreSQL 16 with Prisma 6 (versioned SQL migrations)
FrontendReact 19, Create React App, Tailwind CSS, React Router 6, Axios
LoginShort JWT + rotating refresh token in an httpOnly cookie
PasswordsArgon2id
Validationclass-validator; unknown fields are rejected
LoggingPino (structured JSON, one id per request)
OpsDocker Compose, GitHub Actions CI

Not used on purpose (yet): Redis, queues, Kafka, Elasticsearch, Kubernetes, microservices, S3. None of them solves a problem we have today, and each can be added later without a rewrite. The old Express + MongoDB backend has been removed. It's still in git history at commit dbb1f18.

10How to run it

Full details are in README.md

# first time
docker compose up -d postgres          # or a local Postgres on :5432
cp api/.env.example api/.env           # put a value from `openssl rand -hex 32` in JWT_ACCESS_SECRET
cd api && npm install && npm run prisma:migrate && npm run db:seed

# every time (two terminals)
cd api && npm run start:dev            # → http://localhost:4000
cd frontend && npm start               # → http://localhost:3000

# checks
cd api && npm run test:e2e             # 227 tests

Manual check to do next

Phase 1 steps are below. The Phase 2 browser checklist (school dashboard, members, profiles, reset and verify) is in docs/PHASE2_PROFILES_AND_DASHBOARDS.md §9.

  1. Sign in as the super admin. You should land on /admin.
  2. Reload the page. You should still be signed in.
  3. Create an institution, then Publish it. It should appear on /.
  4. Archive it. On /admin/users, Suspend should be greyed out on your own row.
  5. Sign out. /admin should send you to /login.
  6. Sign in as Carla (student) and open /admin. You should be sent back home.
